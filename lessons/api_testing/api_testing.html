3. API nədir?

nəzəri
💬 Sadə dildə

API — proqramların bir-biri ilə danışdığı “qapı”lardır. Sayt düyməyə basanda arxada bir API sorğusu göndərir.

  • Endpoint — konkret ünvan, məs. /api/products/1/price.
  • Method — nə etmək: GET oxu · POST yarat · PATCH dəyiş · DELETE sil.

4. API recon

nəzəri
🔭 Hücumdan əvvəl məlumat yığmaq
  1. Endpoint-ləri tap: URL-də /api/ nişanları; JavaScript faylları (brauzer hələ çağırmadığı gizli endpoint-ləri açır).
  2. Onlarla necə danışmağı öyrən: hansı method, hansı format (JSON/XML), məcburi/ixtiyari parametrlər, authentication.

5. Lab: API endpoint via documentation

labbitdi

Gizli API sənədini (Swagger/OpenAPI) tapıb istismar etmək.

🎯 Məqsəd

Açıq qalmış API sənədini tap və carlos-u sil. Giriş: wiener:peter.

🔧 Nə etdik
  1. Giriş etdik, email dəyişdik → sorğu: PATCH /api/user/wiener.
  2. Yolu addım-addım qısaltdıq: /api/user/wiener → /api/.
  3. /api/ interaktiv sənəd səhifəsini açdı. İçində DELETE /api/user/{username} var idi.
  4. carlos ilə DELETE-i işlətdik → silindi.
💡 Niyə işlədi

Developer sənədi gizlətməmişdi — sadəcə ünvanını heç kimə deməmişdi. Endpoint-in “base path”-ini (yuxarı yolunu) yoxlamaq açıq qapını tapdı.

🛡️ Necə qarşısı alınır

Sənəd public olmamalıdırsa gizlət. DELETE kimi əməliyyatlara authorization qoy (hər kəs başqasını silə bilməməlidir).

6. Lab: Unused API endpoint

labbitdi

Eyni endpoint-in fərqli HTTP method qəbul etməsini istismar etmək.

🎯 Məqsəd

Gizli endpoint ilə l33t Leather Jacket-i al ($1337).

🔧 Nə etdik
  1. productPrice.js faylında endpoint tapdıq: GET /api/products/1/price.
  2. Repeater-də method-u dəyişdik: GET → PATCH, body: {"price":"$0.00"}.
  3. Qiymət sıfır oldu → cart-a atıb aldıq.
💡 Niyə işlədi

Developer yalnız GET-i düşünüb qorumuşdu; PATCH method-u açıq qalmışdı (“unused/unintended”). Qiymət client tərəfdən dəyişdirilə bildi.

🛡️ Necə qarşısı alınır

İcazəli HTTP method-ları allowlist et. Qiymət kimi həssas dəyərlər heç vaxt client-dən qəbul olunmamalıdır.

7. Lab: Mass assignment

labbitdi

Serverin daxili obyektindəki gizli sahəyə özün dəyər yazmaq.

🎯 Məqsəd

Jaketi al.

🔧 Nə etdik

GET /api/checkout cavabı serverin tam obyektini göstərdi:

{"chosen_discount":{"percentage":0},
 "chosen_products":[{"product_id":"1",...}]}

Amma brauzerin göndərdiyi POST /api/checkout yalnız chosen_products göndərirdi. Biz POST body-yə gizli sahəni əlavə etdik:

{"chosen_products":[{"product_id":"1","quantity":1}],
 "chosen_discount":{"percentage":100}}

→ 100% endirim, pulsuz aldıq.

💡 Niyə işlədi

Server chosen_discount sahəsini daxili obyektdə saxlayırdı; client onu göndərmirdi, amma server göndəriləni avtomatik qəbul edirdi (auto-binding). GET cavabı bizə gizli sahənin adını göstərdi.

🛡️ Necə qarşısı alınır

İstifadəçinin dəyişə biləcəyi sahələri allowlist, chosen_discount kimi həssas sahələri blocklist et.

8. API müdafiəsi (yekun)

nəzəri
🛡️ Qaydalar
  • Sənəd public deyilsə gizlət; public-dirsə güncəl saxla.
  • HTTP method-ları allowlist et.
  • Content-Type-ı yoxla; xəta mesajları generic olsun (detal sızdırma).
  • Köhnə API versiyalarını da qoru.
  • Mass assignment: dəyişilə bilən sahələri allowlist + həssasları blocklist.

9. Lab: Server-side parameter pollution (query string)

lab · practitionerbitdi

Günün ən çətini. Sayt sənin dəyərini daxili API-yə encode etmədən ötürəndə, sən həmin daxili sorğunu dəyişirsən.

🎯 Məqsəd

administrator kimi gir və carlos-u sil (giriş məlumatı verilmir!).

💡 Əsas model (analogiya)

Sən resepsiyaçıya (sayt) “Carlos” deyirsən. O, arxa otaqdakı baş kompüterə (daxili API) öz sözləri ilə yazır — və sənin görmədiyin sahələri də əlavə edir:

username=carlos&field=email&type=email   ← sən yalnız "carlos" yazmısan

Əgər resepsiyaçı sənin yazdığını encode etmirsə, sən # və & ilə bu kağızın quruluşunu poza bilərsən.

🔧 Addım-addım nə etdik
  1. Adi login işləmir — şifrəni bilmirik. “Forgot password?” axını üzərindən getdik: POST /forgot-password, username=carlos.
  2. Truncation (%23 = #): username=carlos%23foo → cavab: “Field not specified.”
    → `#` özündən sonrakını kəsdi (`&field=...` yoxa çıxdı). Demək, gizli bir field parametri var imiş — adını belə öyrəndik.
  3. Inject (%26 = &): username=carlos%26field=username → cavab xam “carlos” qaytardı.
    → `&` yeni parametr başlatdı; `field` iki dəfə yazıldı, server birincini (bizimkini) götürdü (bu sistemin davranışı belədir).
  4. Həssas sahəni oğurla: username=administrator%26field=reset_token → cavab: 
    {"result":"qu4vp...sgvah","type":"reset_token"}
    → `reset_token` normalda yalnız email-ə gedən gizli koddur; `field` ilə onu birbaşa serverdən aldıq.
  5. İstismar: GET /forgot-password?reset_token=qu4vp... → yeni şifrə qoyduq → administrator kimi girdik → admin panelindən carlos-u sildik.

Doğru field adını (reset_token) öz təxminlərimiz tükənəndən sonra tapdıq — real pentest-də bu addım Intruder (söz siyahısı ilə brute-force) və ya sənəd/mənbə araşdırması ilə edilir.

💡 Niyə işlədi

Sayt username-i daxili sorğuya encode etmədən qoyurdu → #/& öz mənasını saxladı. field parametri “istənilən sahəni qaytar” məntiqinə malik idi, developer isə reset_token kimi həssas sahəni siyahıdan çıxarmağı unutmuşdu. (Bu, mass assignment-in əksi: orda gizli sahəyə yazdıq, burada gizli sahəni oxuduq.)

🛡️ Necə qarşısı alınır
  • Client dəyərini daxili sorğuya qoyarkən encode et (SSPP-nin kökü budur).
  • field kimi parametrləri dar allowlist et.
  • reset_token kimi həssas sahələr heç vaxt belə ümumi mexanizmlə qaytarılmamalıdır.

10. SSPP: REST path · struktur data · avtomat alətlər

nəzəri
🧭 REST path-də (query string yox, yolun içində)

Parametr URL yolunun bir hissəsidir: /api/users/123. Burada & işləmir — bunun yerinə path traversal (../) işlədirsən:

name = peter%2f..%2fadmin          (%2f = /)
→ /api/private/users/peter/../admin
→ normalize → /api/private/users/admin

cd peter/../admin kimi: .. səni geri çıxarır, sonra başqa yerə aparır.

🧱 Struktur data (JSON) içində

Server sənin adını JSON-a encode etmədən qoyursa, JSON-u qırıb yeni sahə əlavə edirsən:

Sən:      name = peter","access_level":"administrator
Serverdə: {"name":"peter","access_level":"administrator"}

(JSON input-dursa \" ilə escape edirsən.) Eyni şey cavabda da baş verə bilər.

🤖 Avtomat alətlər
  • Burp Scanner → “suspicious input transformation” tapır (Community-də yoxdur).
  • Backslash Powered Scanner (BApp) → input-ları boring / interesting / vulnerable təsnif edir.
🛡️ Necə qarşısı alınır

Encode olunmayan icazəli simvolları allowlist et, qalan bütün input-u daxili sorğuya qoymazdan əvvəl encode et. Formatı da yoxla.

11. Lab: SSPP in a REST URL

lab · expertbitdi

API testing-in ən çətin lab-ı: path traversal + sənəd kəşfi + reset token.

🎯 Məqsəd

administrator kimi gir, carlos-u sil.

🔧 Addım-addım nə etdik
  1. Path traversal işləyirmi? username=foo%2f..%2fadministrator → admin email qaytardı. Yəni foo/../administrator → administrator-a normalize olundu. ✅
  2. Struktur ipucu: username=administrator%2ffoo → “Invalid route. Please refer to the API definition” → demək bir API sənədi var.
  3. Sənədi oxu: username=foobar%2f..%2f..%2f..%2f..%2f..%2fopenapi.json%23 → server 500 ilə bütün OpenAPI faylını geri qaytardı. Orada yol: /api/internal/v1/users/{username}/field/{field}.
  4. Reset token-i oğurla: username=foobar%2f..%2f..%2f..%2f..%2f..%2fapi%2finternal%2fv1%2fusers%2fadministrator%2ffield%2fpasswordResetToken%23 → cavab: 
    {"type":"passwordResetToken",
 "result":"hmwcba8ze7ju0kede9aj861kuqwtpdgv"}
  5. İstismar: /forgot-password?passwordResetToken=... → yeni şifrə → admin login → admin paneldən carlos silindi.

Niyə 5 × ../? Çünki /api/internal/v1/users/foobar-dan root-a qalxmaq üçün 5 seqment geri getmək lazımdır. %23 (#) serverin əlavə etdiyi /field/email quyruğunu kəsir.

💡 Niyə işlədi

Sayt username-i daxili URL yoluna encode etmədən qoyurdu. ../ ilə yolda yuxarı qalxıb istədiyimiz daxili endpoint-ə getdik. Həssas passwordResetToken sahəsi ümumi {field} mexanizmindən çıxarılmamışdı. Üstəlik 500 xətası bütün sənədi sızdırdı.

🛡️ Necə qarşısı alınır
  • Input-u daxili yola qoymazdan əvvəl encode et (/, . təsirsizləşsin).
  • passwordResetToken kimi həssas sahələri allowlist-dən çıxar.
  • Daxili API xətalarını olduğu kimi geri qaytarma.
