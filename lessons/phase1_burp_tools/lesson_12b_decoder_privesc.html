Dərs 12b. Base64 token-i dəyişib admin olmaq

bitdi

Dərs 3-dəki {"user_id":1,"is_owner":false} nümunəsini real, sınaqdan keçirilə bilən lab etdik: yeni /vuln/profile + /secure/profile.

🔧 Lab necə işləyir

/vuln/profile URL-dən ?token=... alır — token Base64-də {"username":"wiener","role":"user"} kimi bir JSON-dur. İmza yoxdur — server sadəcə decode edib içindəki role-a güvənir.

🧪 Nə etdik
  1. /vuln/profile açdıq → öz token-imizi gördük, rol: user.
  2. Token-i Decoder-ə kopyaladıq → Decode as Base64 → {"username":"wiener","role":"user"} çıxdı.
  3. Mətndə "role":"user" → "role":"admin" etdik.
  4. Yeni mətni Encode as Base64 etdik → yeni token aldıq.
  5. Bu yeni token-i URL-ə qoyub açdıq: Admin panel göründü — "sistemin açarı 12345" sızdı. Parol lazım olmadı, heç bir giriş etmədik.
  6. Eyni saxta token-i /secure/profile-da sınadıq → işləmədi, yenə adi istifadəçi göründü.
🛡️ Niyə işlədi · necə qorunur
  • Niyə işlədi (vuln): server token-in içindəki role sözünə kor-koranə güvəndi. Base64 isə imzasızdır — hər kəs açıb dəyişə bilər (Dərs 12-də gördük: encoding = format, sirr deyil).
  • Niyə işləmədi (secure): secure/profile token-dən yalnız username-i oxuyur, əsl rolu həmişə bazadan (prisma.user.findUnique) yoxlayır. Token nə yazsa yazsın, fərq etməz.
  • Ümumi qayda: client-in göndərdiyi heç bir dəyərə (cookie, token, parametr) icazə/rol üçün birbaşa güvənmə. Əsl JWT-də bu problem imza ilə həll olunur (server imzanı yoxlayır, dəyişdirilmiş token rədd olunur) — biz bunu bilərəkdən imzasız qurduq ki, fərqi əllə görək.

Bağlı: Dərs 3 (encoding), Dərs 12 (Decoder).
