Dərs 2. Cookie, token və sessiya

bitdi

Sayt məni login-dən sonra necə “tanıyır”? Praktika: real bir SaaS panelində öz hesabımın trafikinə baxdıq (yalnız müşahidə).

🔧 Öyrəndiyimiz (idman zalı kartı misalı)
  • HTTP heç nəyi xatırlamır (stateless). Hər request ayrıdır.
  • Login = vəsiqə (email + parol), yalnız bir dəfə göndərilir.
  • Server cavabında kart verir: ya Set-Cookie, ya da body-də token.
  • Brauzer kartı hər sorğuda geri göndərir: Cookie: ... və ya Authorization: Bearer eyJ...
  • Kartı kim tutursa, sayt onu “sən” hesab edir. Parol lazım deyil.
POST /auth/login   {"email":"...","password":"..."}   ← vəsiqə
→ 200 OK  {... "token": "eyJ..." }                     ← kart

GET /client/setting
Authorization: Bearer eyJhbGci...  .  eyJ1c2VyX2lk...  .  zp9DGe...
                      başlıq          məlumat            İMZA
🧪 Repeater-də nə sınadıq
  • Token ilə → 200 OK
  • Authorization sətrini sildim → 401 Unauthorized (“səni tanımıram”)
  • Token-in son hərfini dəyişdim → 401: imza pozuldu, JWT saxtalaşdırıla bilmir
  • Logout etdim, köhnə token-i göndərdim → 200: logout yalnız brauzerdə idi, token exp-ə qədər (1 saat) işləyir

JWT məlumat hissəsi şifrəli deyil, sadəcə Base64-dür: user_id, is_owner, exp hamısı oxunur. Dəyişmək isə olmur, imza qoruyur.

🛡️ Necə qorunur
  • 401 = kim olduğunu bilmirəm · 403 = bilirəm, amma icazən yoxdur.
  • Cookie atributları: HttpOnly (JS oxuya bilməz → XSS oğurlaya bilməz) · Secure (yalnız HTTPS) · SameSite (CSRF-ə qarşı) · Expires.
  • Token JS-də saxlanırsa, XSS onu oğurlaya bilər → XSS-in qarşısını almaq xüsusilə vacibdir.
  • Logout serverdə də olmalıdır: token denylist və ya qısa ömürlü access token + ləğv edilə bilən refresh token.
  • Login cavabında lazımsız həssas sahələr (PIN, hash və s.) qaytarılmamalıdır → Information disclosure.
